# 通用工程技能：领域纯逻辑解耦与测试驱动防回归

## 1. 适用场景
- 任何涉及业务状态机流转、权限/前置门禁、数量/金额/库存计算、数据解析（条码/CSV/协议）或缺陷修复的开发任务。
- 与具体 AI Agent、前端框架或后端语言无关，可在任意项目中直接复用。

---

## 2. 核心工程铁律（MUST）

### 2.1 纯逻辑与界面/IO 严格分离
- **业务规则禁止散落在按钮 `onClick` 中**：所有状态流转、边界校验、数量扣减、排序筛选与映射转换，必须抽离到独立的纯函数或领域服务模块（例如 TypeScript 的 `src/utils/*.ts`、C# DDD 的 `Domain/` 层）。
- **无副作用与可注入时间/依赖**：领域纯函数不得直接依赖 `window`、DOM 或不可控系统时钟（默认参数 `now = new Date()` 可注入），保证单元测试 100% 确定性。
- **非法状态不可表示、越权操作必抛错**：前置门禁（如未完成上一步骤、数量越界、状态非法）必须在领域层抛出语义清晰的异常，绝不依赖“前端把按钮藏起来”。

### 2.2 改 Bug 先补复现测试，做功能必测边界
每次改动必须覆盖以下 4 类用例（而不只是“正常跑通一次”）：
1. **标准主路径（Happy Path）**：完整端到端状态流转。
2. **部分/拆分路径（Partial / Split）**：分批完成、部分成功与部分失败混合。
3. **极端零值/满额路径（Boundary / All-Fail）**：数量为 0、100% 拒绝、空列表、重复提交。
4. **越权与防呆拦截（Guard / Rejection）**：跳过前置步骤、非法输入、历史旧数据反序列化兼容。

### 2.3 验证闭环顺序
1. 先跑单元测试（毫秒级反馈），测试不过绝不进入下一阶段。
2. 再跑静态类型检查与生产构建（确保无隐式类型错误或打包失败）。
3. **仅在最后一次代码改动之后执行的验证才有效**——改完一行代码必须重跑对应检查。

---

## 3. 禁止的反模式（DON'T）
- ❌ **禁止通过删改原有断言来“凑绿灯”**：除非业务规则本身被用户明确变更。
- ❌ **禁止只做静态阅读就宣称修复成功**：必须实际执行测试命令并观察退出码为 `0`。
- ❌ **禁止用 `||` 或默认值静默吞掉必填校验错误**（如表单空值偷偷填假数据绕过校验）。
